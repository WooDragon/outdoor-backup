# Changelog

## [Unreleased]

### Changed
- Current package build metadata in `Makefile` is `PKG_VERSION` `1.2.0` and `PKG_RELEASE` `4` (`1.2.0-4`). The runtime package now depends on `jq` as well as `rsync`. This Unreleased section records development work. No external release evidence was checked for this documentation update, and this entry does not mark a release. The historical `[v1.1.0] - 2025-01` section remains unchanged below.
- Replaced the backup lock's non-atomic `echo $$ > backup.pid` + read-back verification with a single atomic `ln -s "/proc/$$" "$LOCK_LINK"`; the `flock`-based design considered for this rework was dropped, because `flock` is not in this package's `DEPENDS` and the LED error timer forks a 60-second child that would inherit and keep holding an FD-based lock after the manager exits. An intermediate `mkdir`-plus-separate-pid-file design was tried first and discarded: publishing the lock's existence and its holder identity as two separate filesystem operations leaves a window in which a contender cannot yet tell whether the lock's owner is alive, and no policy for that window is safe — treating the gap as "stale" lets two racers win at once, and treating it as "still alive" wedges every future acquirer behind a holder that died in that exact window, forcing a full-timeout wait forever. The symlink design removes the window itself: the link's target is the holder's own `/proc/$$`, so existence and identity publish in the same syscall, and `ln -s` fails atomically when the name already exists. `ln -sf` is never used in this path — it silently overwrites an existing link, which would destroy the mutual exclusion the atomic failure exists to provide. Liveness and identity checking collapse into a single read: `lock_holder_alive()` reads `$LOCK_LINK/cmdline` through the symlink and matches `LOCK_IDENTITY`; a dead holder leaves the link dangling, so `/proc/<pid>/cmdline` is simply unreadable, which doubles as PID-reuse protection (an unrelated live process now holding the reused PID has a different `cmdline` and is still judged stale). Existence checks use `[ -L "$LOCK_LINK" ]`, never `-e`/`-f`, because a dangling symlink is `-e` false but `-L` true. `readlink`, `kill -0`, the separate pid file, and numeric-PID validation are all gone — none of them are needed once identity and liveness are one read. A process that lost the acquisition race never releases another holder's lock: `release_lock` is a no-op unless this process's own `LOCK_HELD` flag was set by its own successful acquisition. Stale-lock recovery renames the dangling link to a per-PID path with `mv` before `rm -f`ing it, so only the contender whose rename actually succeeds performs the removal. Every contended loop iteration reaches its `sleep` and advances `elapsed` before looping again, so `acquire_lock` always reaches its timeout bound instead of spinning. This entry does not claim a package build, firmware build, CI run, or real-device verification; see `### Verified` for what was actually executed.
- Added the #13 runtime configuration loader. It applies built-in defaults, then the root-owned legacy `backup.conf`, then explicit options from the named `outdoor-backup.config` UCI section.
- Replaced shell sourcing of `/etc/config/outdoor-backup` with `uci` CLI reads. UCI values remain data and are not executed as shell text.
- Changed the factory UCI conffile to contain only its named section. Package upgrades preserve modified conffiles and do not migrate or delete the legacy configuration or existing UCI options.
- Added fail-fast validation for empty or invalid paths, invalid boolean controls, and equal or nested backup and mount paths. Disabled `add` events exit before resource operations; `remove` events retain their cleanup path.
- Configuration failures before resource operations and disabled-event reasons are also recorded in syslog; tests write only to an isolated UCI directory.
- #14a historical milestone: installation and startup initialize only runtime directories and do not pre-create `/mnt/ssd/SDMirrors/.logs`.
- #14b: Added a configured-target guard for `add` events. It requires a nonempty target UUID, an exact writable target mount, matching `block info` UUID, and sysfs proof that source, target, and system backing disks are distinct. It parses complete key-value tokens from `block info`; UUID-shaped text inside a `LABEL` value is not treated as a UUID, and malformed quoting is rejected.
- #14b: Target state is anchored through FD 9. `BACKUP_ROOT` must be a strict target-mount child; static symlink components, target detach, target replacement, and read-only remounts fail closed before success. The guard rejects mounts covering the target mount point, an ancestor of `BACKUP_ROOT`, or a child mount inside the backup tree; mounts in disjoint directories are not rejected. A log-summary write failure and a detached or read-only recheck failure after the summary return nonzero.
- #14b: The guard accepts direct `sd`, `mmc`, and `nvme` devices and the R5S system loop case only when its backing file explicitly names a `/dev/` block partition. Unknown devices, file-backed loops, `dm`, and `md` fail closed.
- `FieldBackup.conf` is now parsed by `card-config.sh` as removable-media data. The manager never `source`s or `eval`s it. The reader exports only `SD_UUID`, `BACKUP_MODE`, `CREATED_AT`, and legacy `SD_NAME`; other syntactically valid assignments are ignored. Malformed records, missing UUIDs, and invalid UUIDs fail without rewriting the card file.
- An initial target-guard failure reports stderr and error-level syslog. It may show the optional red LED, but it does not enter source mounting, `rsync`, alias, lock, or application-log work. The manager closes the target FD before the LED delay child starts. A missing LED preserves a nonzero failure. Disabled `add` events retain zero LED side effects.
- Added LuCI `target_mount` and `target_uuid` fields plus `backup_root` boundary text. The form requires a UUID for `enabled=1` and permits an empty UUID for `enabled=0`. Form validation does not mount or format storage.
- The guard now describes its identity boundary consistently: it matches exact kernel mountinfo paths, rejects symlink components and backup-tree-overlapping mounts, and fails closed for unknown or deleted loop backing that cannot prove identity. The implementation does not claim `openat2` protection or complete real-device compatibility.
- #15a: Automatic backup supports only the PRIMARY direction from an SD card to configured storage. The data-only card reader accepts an existing `REPLICA` value for compatibility, but the manager rejects reverse synchronization with an explicit error. It preserves the existing card configuration and sentinel bytes. It does not run `rsync`, update an alias, create a target UUID leaf, or create a per-backup log. The configured `BACKUP_ROOT` may be created before the manager reads the card, and the application error log records the rejection. This behavior does not claim that mounting a writable card produces no filesystem metadata writes. New card configurations generate `PRIMARY` only. The manager does not convert `REPLICA` to `PRIMARY`. #15 remains open for stable card identity, read-only cards, and cloned cards.
- Added `backup-transfer.sh`. It invokes the production `rsync` command directly, retains the real rsync exit status, uses `--partial`, and records successful `--stats` counters. It does not use `--ignore-existing`, `--append`, `--append-verify`, or `--delete`. Files whose size or modification time differs are eligible for update; an equal-size, equal-mtime content change is outside this comparison.
- Added `status.sh`. It uses `jq` to atomically replace the sole status snapshot, `status.json`, with `current_backup`, `storage`, and UUID-unique history ordered newest first and limited to 20 records. It does not create `history.jsonl` or hand-write JSON.
- The manager writes a running snapshot before transfer. It records zero for progress and rate fields because it does not measure live transfer progress. It records completed statistics from successful rsync output only after the summary write and final target-health and identity checks succeed. It writes a failed terminal state when possible; a terminal-status write failure cannot yield completed status.
- The target free-space guard calls `df` through the anchored target FD after the backup leaf exists. `MIN_FREE_SPACE` defaults to 1024 MB and accepts a non-negative decimal integer; `0` disables the reserve. An unknown `df` value fails closed. The manager labels no-space only when the free-space guard rejects the reserve or rsync diagnostics contain an ENOSPC indication; rsync exits 11 and 12 alone are not classified as full storage.
- Cleanup releases transfer and target descriptors before it starts an LED timer. The manager maps the existing `ERROR_TYPE` values `device_unknown`, `lock_timeout`, `no_space`, `card_config`, `rsync`, and `verify_failed` to the common LED helpers. A rejected card configuration, including an existing `REPLICA` card, now classifies as `card_config` instead of the generic `rsync` transfer failure, because it is a card-side configuration problem, not a transfer problem, and the two require different operator remediation. The `remove`-path `pkill` limitation remains scheduled for #16.
- Merged the card-reader whitelist (`CARD_READER_USB_IDS`, `CARD_READER_PATH_PREFIXES`, `CARD_READER_HEURISTIC_FALLBACK`) into `config.sh`'s single config channel (#2): default < legacy `backup.conf` < explicit `card_reader_usb_ids` / `card_reader_path_prefixes` / `card_reader_heuristic_fallback` options in the named `outdoor-backup.config` UCI section. Previously the hotplug trigger read `backup.conf` directly for these three variables only, a second configuration path alongside the manager's UCI-aware loader.
- **Layering fix (PR #11 review)**: `config_load` now only *assigns* the three `CARD_READER_*` fields; it no longer validates them. A new `config_validate_card_reader` function owns that validation — same rules as before (`card_reader_usb_ids` must be space-separated `vvvv:pppp` hex tokens, normalized to lowercase on success; `card_reader_path_prefixes` entries must be absolute and free of `*`/`?`/`[`; `card_reader_heuristic_fallback` must be `yes` or `no` — each violation is a `config_error` naming the offending field and token), plus two new constraints on `card_reader_path_prefixes`: the bare `/` is rejected (it would match every `DEVPATH`, silently disabling the whitelist), and a `.` or `..` path segment is rejected. The token/prefix split loops still run under `set -f` and restore it on every return path, success or failure. `config_validate_card_reader` is called only by the hotplug trigger, its sole consumer — never by `config_load`. This fixes a real bug: `backup-manager.sh` calls `config_load "$BASE_DIR/conf/backup.conf" || exit 1` at line 47, before `trap cleanup`, `main()`, and `handle_remove` are installed, but the manager never reads `CARD_READER_*`. With validation folded into the shared loader, an invalid whitelist made the manager `exit 1` on a `remove` event for a field it doesn't consume — skipping `pkill rsync` and the `trap cleanup` unmount/lock-release on physical card removal. Moving the validation to its only consumer removes that failure mode entirely; `backup-manager.sh` itself is unchanged.
- The hotplug trigger sources `config.sh` behind a `[ -r ]` readability test rather than relying on the `.` builtin's exit status. `.` is a POSIX special builtin: on `openwrt/rootfs:x86_64-24.10.8` a `. /missing-file` inside `if ! ...` terminates the whole script with status 2 and the following line never runs, so an exit-status guard is dead code and a missing loader would kill the trigger outright, taking the `remove` cleanup path with it. `test-card-reader.sh` R14 covers this and was confirmed to fail on the exit-status form.
- The hotplug trigger (`90-outdoor-backup`) no longer sources `backup.conf` at file-load time. It now calls a `load_reader_config` function — sourcing `config.sh` and calling `config_load` — only from inside the `add` branch (after the partition-type guard) and the `remove` branch, so an ignored block event never pays the `uci` lookup cost. `load_reader_config` never aborts the hotplug trigger over a config problem: a `config_load` failure is only logged, and — since #11's layering fix above — `config_validate_card_reader` is then called unconditionally regardless of whether `config_load` succeeded; if it rejects the whitelist, `load_reader_config` resets `CARD_READER_*` to the degraded default (empty whitelist, `fallback=yes`) itself, rather than relying on any assumption about what `config_load` left behind. `backup-manager.sh`'s own `config_load` call remains the real fail-closed gate, and — now that card-reader validation is out of the shared loader — it only covers the fields the manager actually reads.
- `config_load`'s legacy-file source now checks `[ -f ] && [ -r ]` before running `.` on it, instead of the bare `[ -f ]` used previously. `.` is a POSIX special builtin: sourcing a file that cannot be opened terminates the *whole calling script*, not just the function — the same failure mode `90-outdoor-backup`'s `CONFIG_SCRIPT` guard (below) was already written to avoid, just for a different file. A `backup.conf` that exists but cannot be read (root-owned, wrong mode, or — as constructed in `test-card-reader.sh` R17 — a path that resolves to a directory rather than a regular file) now makes `config_load` return a `config_error` and fail closed, instead of either silently skipping it (treating "can't read" the same as "doesn't exist") or letting `.` kill the caller outright.

### Card Reader Config Migration Notes (#2)
- `backup.conf`'s `CARD_READER_*` comments now document the UCI equivalents and state that an explicitly-present UCI option takes precedence; the variable names and defaults are unchanged, so an unmodified existing `backup.conf` behaves exactly as before.
- No LuCI form field was added for these three options in this change; they are UCI-settable only via `uci set` / `uci commit` for now.
- **Read-only source card mount (#15)**: `mount_sdcard` now takes a mandatory `ro`/`rw` mode argument — there is no default, because a missing mode is a caller bug that must fail loud rather than silently pick one — and the `add` path mounts the source card `ro`. `rsync` therefore always reads from a read-only mount, and the steady state has no code path that can write to the card at all.
- **Failure-safe first-time provisioning (#15)**: the only exception is a card with no formal `FieldBackup.conf`. That case unmounts the read-only source and opens a bounded `rw` window. It creates a unique temporary file in the same directory, checks the complete write, and publishes it by rename. It checks `sync` after publication. A failed `rw` mount or a failed write means that the manager cannot initialize the card; neither condition alone proves every form of write protection. A failed `sync` stops the run with a distinct error. Rename does not prove power-loss durability. Existing symbolic links and other non-regular objects at the formal name are rejected. The manager then attempts to restore a read-only mount and rereads the formal file only as a flow check. That reread is not proof of persisted media contents or card identity. Cleanup attempts an unmount after failures but cannot guarantee a restored read-only mount. The implementation uses unmount plus mount because its supported filesystems do not share uniform `remount` behavior; this is an implementation choice, not a universal filesystem rule.
- `test-target-manager.sh` now injects the first and second source unmount failures independently. The first blocks the read-write window. The second blocks read-only restoration and transfer. It injects partial temporary-file writes, temporary-file creation failures, publication failures, and post-publication `sync` failures. It verifies that the unpublished paths leave no formal configuration and clean only the temporary file created by the run. It verifies that a retry after a temporary write failure can initialize the card. It also rejects a dangling configuration link and a configuration directory. M16 records the stubbed `rw`, publication, and read-only restoration-attempt order; it does not claim a real-media persistence result.
- All of these failures are classified `card_config`, which reaches the operator as the manual-toggle red LED pattern and error-level syslog. Note that they do **not** produce a `status.json` record: `write_failed_status` is gated on `STATUS_STARTED`, which `perform_backup` sets only after `write_running_status` succeeds, and every failure in this sequence happens strictly before that point. That observability gap is pre-existing and shared with every other pre-transfer rejection (see the existing REPLICA-card case); it is recorded here, not fixed in this change.

`config_load` *succeeding* (layering) while `config_validate_card_reader` fails loud on a malformed `card_reader_usb_ids` token, a relative/glob-containing/bare-`/`/`..`-containing/`.`-containing (both an interior `/./` and a trailing `/.`) `card_reader_path_prefixes` entry, and an invalid `card_reader_heuristic_fallback` value; an unrelated `config_load` failure (bad `backup_root`) not aborting hotplug whitelist detection, with `set -f` restoration checked directly against `config_validate_card_reader` on both its failure and success paths (isolated from any detection function); the pre-existing heuristic-behavior scenarios (1TB+ card rescued by whitelist, model-string match, path-string match, strict-mode-blocks-all, case-insensitive VID:PID); an unreadable `config.sh` leaving the trigger alive on the built-in heuristic instead of dying inside the `.` builtin; a mutation probe that deletes the UCI-precedence `config_apply_uci_option` call for `card_reader_usb_ids` and proves the precedence assertion goes red; an invalid UCI whitelist genuinely resetting to the degraded default (proven by pairing it with `card_reader_heuristic_fallback=no`, so a match is only possible if the reset actually overrode that back to `yes`) rather than merely being logged, and never logged with the retired "unrelated" wording; the `uci` CLI being unavailable while the UCI conf file exists, proving `config_load` fails before any UCI value is ever applied and the hotplug trigger falls back to the legacy value, not a partially-applied UCI one; a `backup.conf` that exists but cannot be sourced (constructed as a directory, since the pinned rootfs runs as root and chmod bits do not apply) failing `config_load` closed without killing the hotplug trigger; and a mutation probe for `config_validate_card_reader`'s own `set -f` restoration on its usb_ids failure branch, which fails loud if its target line cannot be located.
- `test-target-manager.sh`'s mock `mount` stub used to unconditionally materialize a fixed-UUID `FieldBackup.conf` after every mount. That auto-provisioning precondition obscured coverage of the first-write and read-only-card paths. Removing it turned M03, M03b, and M04's UUID sub-case red (6 assertions), which shows that those cases depended on the precondition. It does not establish that the prior M03b scenario never occurred; the revised fixtures now opt in explicitly to each required card state. The stub also no longer hardcodes `$4` as the mountpoint — it scans for the final positional operand and records the `-o` mode, so it stays correct as the argv shape changes — and a `umount` stub was added because the production code now calls `umount` directly. Four cases were added: M13 (a card with an existing config produces exactly one `ro` mount, never any `rw` mount, and its config bytes are unchanged by sha256), M14 (a blank card produces exactly the sequence `ro, umount, rw, umount, ro` and ends read-only), M15 (an injected `rw` mount failure fails the run with the write-protected reason, creates no config file, and never reaches `rsync`), and M16 (an injected failure of the *second* `ro` mount fails the run after the config write succeeded, with the restore-failure reason, and never reaches `rsync`). The `ro` failure injector counts only `-t auto` attempts, because `mount_sdcard` retries six further filesystem types within one logical invocation and a naive per-call counter would let the intended failure be rescued by the next retry. The mount-sequence assertions were mutation-checked by changing both the initial read-only mount and the restoration read-only mount to `rw`; that change turns 11 assertions red across M03, M04, M13, M14, M15, and M16.
- `test-lock.sh` was fully rewritten against the atomic symlink lock: it runs the delivered `acquire_lock`/`release_lock`/`lock_holder_alive` functions verbatim (extracted from `backup-manager.sh` by marker, not retyped) as real per-process ash instances inside the pinned rootfs, covering concurrent contention with exactly one winner, release after contention, a non-owner's `release_lock` never deleting a live holder's lock, a dangling-link reclaim of a dead-PID lock within timeout, a live holder whose `cmdline` does not match `LOCK_IDENTITY` still being judged stale (the PID-reuse guard, now expressed as an identity mismatch rather than a numeric-PID check), a genuinely alive identity-matching holder blocking reclaim for its full hold window, a bounded-timeout case that asserts the real `sleep` call count equals `timeout/interval`, a `SIGKILL`ed holder's lock being reclaimed by the next acquirer, a lingering background child not retaining the lock after release, `release_lock` idempotency, an explicit invariant that the lock link never exists without an immediately usable holder identity (replacing the retired empty-pid-window scenario the mkdir-based design needed), and a mutation probe that swaps the atomic `ln -s` publish for `ln -sf` and proves the suite's own concurrent case then observes every racer "win" simultaneously. Before this fix landed, the same new suite run unmodified against the prior `backup-manager.sh` (the pre-issue-#8 naive echo/readback design, which predates even the `mkdir` iteration) failed immediately at setup because that file had no `lock_holder_alive` function to extract; run against the fix it passes 13/13 cases and 45/45 assertions, confirmed stable across repeated runs with no flakiness.
- `test-target-manager.sh` deleted each case directory while the LED timer subshell started by the previous case was still looping and starting new stub sleep processes, so joining a single one could not settle it and the survivors failed to open paths that had just been removed. That noise reached the asynchronous stderr probe and failed the suite intermittently. Each case now owns its directory and the whole tree is removed once when the suite ends; assertions and scenarios are unchanged. The unmodified suite reproduced the failure on the prior code, and ten consecutive runs of the fixed suite passed.
